Architecture A · chunk-based data parallelism · POSIX threads

How far does chunked pthreads scale, and when is it not worth it?

Shot-boundary detection over raw BGR video: each worker claims contiguous frame chunks from a mutex-guarded counter, computes a 64-bin HSV histogram per frame, and writes a disjoint slice of the output. A serial adaptive threshold runs after the join. This page measures that design against a single-threaded loop on one laptop, under Windows and Linux.

Intel i5-13450HX · 6 P-cores + 4 E-cores · 16 hardware threads · 15.7 GB RAM · Windows 11 (MinGW-w64 GCC 16.2, winpthreads) · WSL2 Ubuntu 24.04 (GCC 13.3, NPTL) · -O2 · warm page cache · synthetic 160×90 video unless noted · median of ≥7 runs

01Speedup by worker count

With plenty of data, speedup is near-linear up to 4 workers and then flattens. The bend comes after the 6 P-cores are busy: extra workers land on hyper-thread siblings and E-cores, which add less each. The Windows run with an unpinned baseline looks better than it is, because Windows often ran the single-threaded baseline on an E-core (see section 07).

03Where threading starts to win

Speedup against the number of frames. The line at 1.0× is break-even. At 160×90 (≈50 µs of work per frame) threads win from about 8–16 frames. At 32×18 (≈2 µs per frame) the same fixed cost needs about 256 frames to pay off. Measured in work rather than frames, both cross at roughly 0.5 ms of sequential work on Linux and 1 ms on Windows.

05Chunk size and redundant work

Each chunk re-reads and re-processes the frame just before it, so the first difference in the chunk is correct. That is min(P·c, N) − 1 extra frames per run. With many small chunks this adds up: 8 workers × 64 chunks on 256 frames gives one-frame chunks and nearly doubles the work. Smaller chunk counts also mean fewer seeks. One to four chunks per worker is best on this machine. More chunks only help when the cores run at very different speeds.

06What the extra workers cost in CPU time

Wall time stops improving after about 8 workers, but total CPU time keeps rising. At 16 workers the job uses 1.7× (Linux) to 2.3× (Windows) the CPU time of the sequential loop for the same frames. Work on a hyper-thread sibling or an E-core takes more CPU-seconds per frame. On Windows, 35–50% of worker CPU time is kernel time, nearly all of it copying frames out of the file cache in ReadFile. On Linux it is 10–15%.

07Hybrid cores change the baseline

The same histogram loop, pinned with start /affinity, is 2.6–5.4× slower on an E-core than on a P-core. When left to the scheduler at normal priority, Windows often placed the single-threaded baseline on an E-core. That makes the sequential time 1.7–2.7× too slow and every speedup computed from it too high. For a fair comparison, pin the baseline to a P-core or run it at high priority.

08What to change in arch_a.c

  • Add a sequential fallback. Estimate the work as N × tframe and run single-threaded under about 1 ms. Otherwise use P = min(P-cores, work ÷ ~100 µs).
  • Cap workers near the P-core count. On this machine, going past 8 gives at most 10–20% more wall-clock speed for 50–100% more CPU time.
  • Use a minimum chunk length, not a fixed count per worker. Chunks of at least 64 frames keep the overlap re-read under 2%.
  • Memory-map the video (mmap / CreateFileMapping) instead of fread. This removes one syscall and one kernel copy per frame, the main source of the 35–50% kernel time on Windows. It also removes the per-worker fopen.
  • Reuse threads through a small pool when the detector or the scene-similarity stage is called repeatedly. That saves 0.1–0.6 ms of spawn and join per call.
  • Leave the mutex alone. It costs 18–60 ns per claim across about 4P claims per run, well under 0.01% of run time.
